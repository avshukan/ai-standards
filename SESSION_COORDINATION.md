# Session Coordination Protocol

## 1. Purpose

Session Coordination Protocol определяет порядок управления несколькими рабочими сессиями ChatGPT.

Цели:
- разделять большие задачи на самостоятельные сессии;
- отслеживать родительские и дочерние связи;
- сохранять результаты при передаче между сессиями;
- показывать план и прогресс;
- различать жизненный цикл сессии и результат работы;
- обеспечивать предсказуемое закрытие и возобновление.

Протокол универсален и не привязан к конкретному ChatGPT Project, Git-репозиторию или предметной области.

Протокол не заменяет источники истины конкретного проекта.

## 2. Session-centric model

Каждая сессия отвечает за:
- собственную цель и scope;
- собственный план, если он существует;
- собственный lifecycle;
- созданные дочерние сессии;
- полученные результаты;
- интеграцию этих результатов;
- подготовку своего дистиллята.

Различать:

Project truth — актуальные факты, решения и состояние проекта.

Session knowledge — информация, фактически доступная конкретной сессии.

Нельзя считать знания сессии автоматически синхронизированными с другими чатами.

## 3. Session hierarchy

Сессия может быть:
- самостоятельной;
- дочерней по отношению к другой сессии;
- одновременно дочерней и родительской.

При создании дочерней сессии необходимо передавать:
- имя родителя;
- роль родителя;
- статус родителя на момент делегирования;
- цель дочерней сессии;
- границы работы;
- условия передачи результата.

Обычный маршрут:

Grandchild → Child → Parent

Прямая передача результата через несколько уровней допускается.

Она не означает автоматической интеграции результата промежуточными сессиями.

Если родитель неизвестен, его не нужно придумывать.

## 4. Session roles

Предусмотрены роли:

| Role | Responsibility |
|---|---|
| Coordinator | Планирование, делегирование и интеграция |
| Research | Исследование и проверка источников |
| Implementation | Реализация в согласованном scope |
| Review | Независимая проверка |

Роль не предоставляет дополнительных технических прав.

Research и Review обычно read-only, если не согласовано иное.

Implementation действует в пределах задачи и доступных инструментов.

Coordinator не должен самостоятельно принимать существенные пользовательские решения.

В компактных таблицах роль `Coordinator` отображается как `Lead`.

Canonical role в данных и промптах остаётся `Coordinator`.

## 5. Session lifecycle

Существуют два состояния:

- `active` — сессия открыта;
- `closed` — сессия завершена.

Поддерживаются переходы:

active → closed

closed → active, только по явной команде пользователя.

Не смешивать lifecycle с результатом работы.

Например:

session_status: closed
work_outcome: blocked

Это завершённая сессия с заблокированной работой.

Рекомендуемые значения work_outcome:

- completed
- partial
- blocked

Закрытая сессия не продолжает содержательную работу без явного возобновления.

Это правило поведения, а не техническая блокировка интерфейса ChatGPT.

## 6. Session commands

### `статус сессии`

Показать текущее состояние в Display mode:

- Session Status;
- Session Tree;
- Session Plan, если существует.

### `дистиллят`

Создать snapshot:

session_status: active

Сессия продолжает работу.

### `дистиллят и завершить`

Применить Completion Guard.

Если завершение разрешено, создать итоговый дистиллят:

session_status: closed

Затем перейти в closed.

### `возобновить сессию`

Разрешить переход:

closed → active

Не создавать новый дистиллят автоматически только из-за возобновления.

Следующий дистиллят получает очередной номер.

## 7. Distillate versioning

Каждый дистиллят содержит:

- имя сессии;
- роль;
- родителя;
- execution environment;
- session_status;
- distillate_version;
- цель и существенный контекст;
- результаты;
- план и его состояние;
- известные дочерние сессии;
- handoff и remaining work.

Версии:
- начинаются с v1;
- увеличиваются последовательно;
- не сбрасываются после возобновления;
- являются неизменяемыми snapshot.

Родитель использует наибольшую полученную версию дочернего дистиллята.

Не путать:
- последнюю полученную по времени версию;
- версию с максимальным номером.

Старый дистиллят не перезаписывает более новый.

Полученный snapshot не гарантирует, что дочерняя сессия не изменилась после передачи.

## 8. Parent knowledge and integration

Отдельно хранить:

session_status
result_integrated

Первое — последнее известное состояние дочерней сессии.

Второе — обработал ли непосредственный родитель полученный результат.

Пример:

session_status: closed
result_integrated: false

Дочерняя сессия завершена, но результат ещё не интегрирован.

Интеграция результата не означает автоматического принятия всех его рекомендаций или архитектурных предложений.

Для известных внуков использовать сведения, полученные через дочерние сессии.

Не предполагать live-синхронизацию.

## 9. Completion Guard

Перед закрытием родителя проверить:

1. Открытые дочерние сессии.
2. Полученные, но неинтегрированные результаты.

Если есть открытые дочерние сессии, приостановить завершение.

Показать:
- имена открытых сессий;
- последние известные статусы;
- версии дистиллятов;
- неполученные результаты.

Предложить три варианта:

1. Отменить завершение.
2. Завершить родителя, оставив детей открытыми.
3. Сначала получить результаты и повторить завершение.

Нельзя выбирать вариант самостоятельно.

Для завершения с открытыми дочерними сессиями требуется явный повторный запрос пользователя с выбранным вариантом.

После разрешения можно сформировать итоговый дистиллят.

Закрытие родителя не закрывает дочерние сессии.

Неинтегрированные результаты:
- требуют предупреждения;
- отражаются в дистилляте;
- сами по себе не блокируют закрытие.

## 10. Session Plan

План может отсутствовать.

Состояния плана:

- `no_plan`
- `draft_plan`
- `approved_plan`

Draft не становится approved без согласования пользователя.

План может состоять из:
- самостоятельных шагов;
- этапов, содержащих шаги.

Для группированного плана использовать два уровня:
- Stage;
- Step.

Статусы этапов и шагов:

- `pending`
- `current`
- `done`
- `blocked`
- `skipped`

Не более одного текущего шага.

Этап `done` означает, что его обязательные шаги выполнены или явно пропущены.

Закрытие дочерней сессии не означает автоматического завершения связанного шага.

Колонки:

- `#`
- `Stage / Step`
- `Status`
- `Session`

В `Session` указывается конкретная делегированная сессия или `—`.

Название должно совпадать с Session Tree.

Пример:

```text
Session Plan · approved_plan

#      Stage / Step                Status    Session
1.     Research                     done      —
  1.1  Проверить требования         done      Research A
  1.2  Проверить ограничения        done      Research B
2.     Implementation               current   —
  2.1  Определить scope             done      —
  2.2  Реализовать                  current   Implementation A
  2.3  Проверить                    pending   Review A
3.     Release                      pending   —
  3.1  Подготовить результат        pending   —
```

Полный план показывать:
- по запросу;
- после утверждения;
- после существенного изменения;
- при завершении этапа;
- при появлении блокера.

Не показывать план после каждого обычного ответа.

Если пользователь просит идти строго пошагово, соблюдать согласованные checkpoints.

Не вводить обязательное подтверждение каждого мелкого шага без запроса.

## 11. Session Tree

Стандартные колонки:

- `Session`
- `Role`
- `Status`
- `v`
- `Int.`

Показывать:
- непосредственного родителя, если он известен;
- текущую сессию;
- всех известных детей;
- всех известных внуков и более глубоких потомков.

Не ограничивать глубину произвольно.

Для связей использовать моноширинные символы:

- `├──`
- `│`
- `└──`

Символ `●` обозначает текущую сессию.

Role:
- Coordinator в таблицах обозначается как Lead;
- остальные роли сохраняют названия.

Status:
- active;
- closed;
- unknown.

`unknown` означает недостаток информации. Это не отдельный lifecycle state.

`v` — максимальная известная версия дистиллята.

`Int.`:
- yes;
- no;
- —.

Интеграция относится к непосредственному родителю.

Пример:

```text
Session Tree

Session                           Role      Status    v   Int.
Main Project                      Lead      unknown   —    —
└── ● Workstream Coordinator      Lead      active    3    —
    ├── Backend Research          Research  closed    2    yes
    │   ├── Crypto Research       Research  closed    1    yes
    │   └── API Review            Review    active    1    no
    └── Mobile Research           Research  active    2    yes
        └── iOS Research          Research  closed    1    yes
```

Не придумывать потомков и их состояние.

## 12. Session Status

Единый набор и порядок полей:

```text
Session Status

Session       Workstream Coordinator
Lifecycle     active
Plan          approved_plan
Progress      Stage 2/3 · Step 2.2
Current       Реализация
Next          Review
Distillate    v3
Children      2 known · 1 active · 1 closed · 0 unknown
Outcome       —
Closed at     —
```

Использовать ту же структуру после завершения.

`Children` считает только непосредственных детей.

Не смешивать их с внуками.

Для закрытой сессии:

- Lifecycle: closed;
- Current: none;
- Outcome: фактический результат;
- Closed at: достоверное время либо unknown.

Не придумывать timestamps.

Постоянные визуальные сигналы:

- 🟢 active
- 🏁 closed
- 🟡 unknown

Цвет дополняет текст, но не заменяет его.

## 13. Display and Transfer modes

Для Session Tree, Session Plan и Session Status существуют два режима.

### Display mode

Используется в обычных ответах ChatGPT.

Предпочтительное представление:
- компактные визуальные таблицы;
- моноширинные связи дерева;
- моноширинные номера плана;
- сдержанные цветные пиктограммы;
- явные текстовые статусы.

Не использовать цвет как единственный носитель информации.

### Transfer mode

Используется для:
- дистиллятов;
- handoff;
- передачи между независимыми сессиями.

Формат:
- Markdown;
- копируемые текстовые таблицы;
- сохранённые отступы;
- отсутствие зависимости от цвета и визуальных компонентов ChatGPT.

Каждый дистиллят выводится одним внешним Markdown code fence из четырёх обратных кавычек. Это единый копируемый блок, содержащий весь дистиллят.

Внутри дистиллята присутствуют:

- Session Status;
- Session Plan;
- Session Tree.

Если плана или дочерних сессий нет, отражать это кратко.

Не создавать фиктивные записи.

## 14. Final closure signal

После полного финального дистиллята вывести краткую отдельную визуальную строку:

🏁 Сессия завершена · v3

Открытых дочерних: 0 · Неинтегрированных результатов: 0

Это не второй дистиллят.

Показывать фактические значения, не подставлять нули автоматически.

В самом дистилляте остаётся полная информация о состоянии.

## 15. Child session prompts

Каждый готовый промпт содержит:

1. Goal.
2. Scope.
3. Relevant context.
4. Accepted decisions.
5. What to verify.
6. Expected output.
7. Out of scope.
8. No unrelated changes.

Обязательно указывать Execution environment:

Для ChatGPT:
- Project;
- new или existing chat.

Для Claude Code / Codex:
- инструмент;
- repository;
- branch/worktree, если существенно.

Execution environment указывается:
- перед промптом;
- внутри промпта.

Не предполагать, что другая среда автоматически имеет доступ к локальным файлам, Project Sources или подключённым сервисам.

Для дочерней сессии также передавать:
- роль;
- родителя;
- статус родителя на момент делегирования;
- цель делегирования;
- требования к дистилляту;
- маршрут передачи результата.

Готовый агентский промпт выдавать одним Markdown-блоком из четырёх backticks.

## 16. Persistence and limitations

Session Coordination Protocol не создаёт автоматически общий реестр сессий.

Разделять:

Session history — история конкретной сессии.

Distillate — snapshot для передачи.

Canonical project sources — долговременные факты и решения проекта.

Передача дистиллята должна реально произойти.

Нельзя считать, что независимая сессия автоматически получила результат.

Не создавать глобальный SESSION_INDEX.md без подтверждённой необходимости.

Не превращать TODO проекта в реестр сессий.

## 17. Adoption in another project

Для внедрения:

1. Разместить протокол в Project Sources.
2. Добавить короткую ссылку в Project Instructions.
3. Проверить отсутствие противоречий с действующими правилами.
4. Проверить отображение Session Status / Tree / Plan.
5. Проверить дистиллят и передачу результата.
6. Проверить закрытие и возобновление.

Сама загрузка файла не гарантирует применения всех правил.

Для важных рабочих процессов провести пилот.
